# Is MMP-C Certificate Renewal Quietly Breaking Intune Enrollment? A Theory Built from Real Devices


For the last several weeks I have been investigating a group of Windows devices that eventually lost their ability to maintain Intune enrollment. The obvious symptom was an expired Intune certificate chain accompanied by enrollment failures such as certificateStore:0x83750005 and XML parsing errors during re-enrollment. Initially, the problem appeared to be nothing more than expired certificates. However, after comparing multiple healthy and unhealthy systems, I started seeing a different pattern emerge. What caught my attention was not the traditional OMA-DM enrollment, but the newer Microsoft Management Platform Cloud (MMP-C) enrollment that Microsoft has begun deploying alongside classic Intune enrollment. As described by Jannik Reinhard in this wonderful article https://jannikreinhard.com/intune-troubleshooting-guide/ and a few others in the endpoint management community (Rudy Ooms = MVP https://www.linkedin.com/in/rudyooms/), MMP-C is Microsoft's newer management plane designed to support Windows Declared Configuration and eventually reduce reliance on the traditional OMA-DM model. The important detail is that every modern Windows device now effectively has two enrollments: the classic OMA-DM enrollment and a linked MMP-C enrollment.


The first clue came from a device that was still fully operational. The device continued receiving policies and had a healthy OMA-DM certificate chain, yet the MMP-C enrollment was recording renewal failures every two days. In the DeviceManagement-Enterprise-Diagnostics-Provider Enrollment log the sequence was consistent: Event 4 (certificate policy request sent successfully), Event 6 (certificate policy response processed successfully), Event 8 (certificate enrollment request sent successfully), followed immediately by Event 52 and Event 11 with HRESULT 0x80190191, an HTTP 401 Unauthorized response. Registry data within the MMP-C enrollment GUID showed RenewStatus=3, RenewErrorCode=80190191, and an enrollment state different from healthy devices. What is significant here is that the request was reaching the service successfully. Policy requests were processed, certificate enrollment requests were submitted, and only after submission did the service reject the request. Removing expired duplicate certificates changed nothing. The same 401 response continued to occur.

To validate this wasn't normal behavior, I compared the device against a fully healthy system. The healthy device showed the same LinkedEnrollment values but had RenewStatus=0, RenewErrorCode=0, and a different enrollment state. Its renewal workflow completed successfully with Event 10 ("Certificate enrollment response parsed successfully"), Event 16 ("OMA-DM client configuration succeeds"), and Event 3005. More interesting was the certificate hierarchy itself. The healthy device used a newer certificate trust path that ultimately leveraged the Microsoft Intune Root Certification Authority issued in September 2025. The unhealthy system's MMP-C enrollment referenced a different root, the Microsoft Device Management Root Certification Authority, with a matching RootCertThumbprint stored in the MMP-C enrollment registry key. At first I dismissed this as a curiosity. However, multiple failing devices exhibited the same root authority, while healthy devices appeared to have transitioned to the newer hierarchy.

The strongest evidence came from comparing three classes of devices. Device C was fully healthy with successful MMP-C renewals. Device B was healthy from an Intune perspective but logged MMP-C renewal failures beginning June 13, 2026. Device A ultimately failed completely with expired certificate chains, XML parsing errors, and enrollment failures. This progression suggested a possible lifecycle: MMP-C enters a failed renewal state, repeatedly receives HTTP 401 responses, continues operating for months because certificates are still valid, and eventually reaches certificate expiration without obtaining replacements. Once the chain expires, enrollment recovery becomes impossible and the device enters the same terminal state observed on Device A. Importantly, the MMP-C renewal errors began long before certificate expiration, suggesting the renewal failure is not caused by expiration but may instead be the precursor to it.
My working theory is that Microsoft has begun relocating portions of enrollment and certificate lifecycle management into the MMP-C platform. If that assumption is correct, an MMP-C renewal failure would no longer be an isolated issue affecting only Declared Configuration workloads. It could potentially prevent OMA-DM enrollment certificates from being refreshed as well. In that scenario, the device would continue functioning until existing certificates naturally expired, after which both management channels would become unsalvageable. I do not yet have proof that OMA-DM certificate renewal explicitly depends on MMP-C, and correlation should never be confused with causation. However, the recurring pattern of MMP-C renewal failures, shared root authority characteristics, enrollment state differences, and eventual device failure suggests there is a deeper relationship that deserves investigation. The next step is determining whether the MMP-C enrollment has become the authoritative path for enrollment certificate renewal and whether devices stuck in a perpetual 0x80190191 renewal state are simply future enrollment failures waiting to happen.
